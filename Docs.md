# Техническая документация Calculatrade

## 1. Назначение приложения

Calculatrade («ИБ-Эффект») — веб-приложение для оценки рисков информационной безопасности, расчёта остаточного риска после внедрения защитных мер и оценки экономического эффекта инвестиций в ИБ.

Приложение позволяет:

- регистрировать пользователей и выполнять вход;
- настраивать критерии оценки риска;
- создавать активы и задавать их стоимость и приоритет;
- описывать угрозы и уязвимости;
- рассчитывать исходный и остаточный риск;
- создавать защитные меры и связывать их с рисками;
- оценивать снижение ожидаемых потерь, ROSI и чистый экономический эффект.

Математические расчёты выполняются на клиенте, чтобы интерфейс оставался реактивным. Сервер отвечает за хранение данных, авторизацию и изоляцию данных пользователей.

## 2. Технологический стек

### Клиент

- **HTML/CSS** — разметка и визуальное оформление;
- **Alpine.js** — реактивное состояние и обработчики интерфейса;
- **Axios** — предусмотренный API-клиент для HTTP-коммуникации;
- **Fetch API** — используется текущей legacy-обёрткой `src/database.js` для запросов к серверу;
- **Vite** — локальный dev-сервер и сборка клиента;
- **localStorage** — хранит только JWT и краткую информацию о сессии, но не данные приложения.

### Сервер

- **Node.js** — среда выполнения;
- **Express.js** — HTTP API и middleware;
- **Prisma ORM** — описание схемы и доступ к PostgreSQL;
- **PostgreSQL 16** — постоянное хранилище;
- **bcrypt** — хеширование паролей;
- **jsonwebtoken** — создание и проверка JWT;
- **cors** — настройка междоменных запросов;
- **dotenv** — загрузка переменных окружения.

### Инфраструктура

- **Docker Compose** — локальный запуск PostgreSQL;
- **npm workspaces** — управление monorepo.

## 4. Запуск проекта

### Требования

- Node.js с npm;
- Docker Desktop или Docker Engine с Compose;
- свободные порты `4000`, `5173` и `5432`.

### Установка

```bash
npm install --workspaces --include-workspace-root
```

### Настройка сервера

Создайте `server/.env` на основе `server/.env.example`:

```env
PORT=4000
CLIENT_URL=http://localhost:5173
JWT_SECRET=replace_with_a_long_random_secret
DATABASE_URL=postgresql://postgres:postgres@localhost:5432/calculatrade?schema=public
```

Для реального окружения `JWT_SECRET` и пароль PostgreSQL необходимо заменить на секретные значения.

### Настройка клиента

При необходимости создайте `client/.env`:

```env
VITE_API_BASE_URL=http://localhost:4000/api
```

Текущая legacy-часть клиента использует `http://localhost:4000/api` как значение по умолчанию.

### Запуск базы и Prisma

```bash
docker compose up -d
npm --workspace server run db:generate
npm --workspace server run db:push
```

`db:generate` генерирует Prisma Client. `db:push` синхронизирует Prisma-схему с локальной базой без создания миграционных файлов.

### Запуск приложений

В отдельных терминалах:

```bash
npm run dev:server
npm run dev:client
```

Адреса:

- клиент: `http://localhost:5173`;
- API: `http://localhost:4000/api`;
- проверка API: `http://localhost:4000/api/health`;
- PostgreSQL: `localhost:5432`.

Клиент следует открывать через Vite или другой HTTP-сервер. Открытие `index.html` напрямую через `file://` не рекомендуется, поскольку API-запросы и CORS в таком режиме могут работать некорректно.

## 5. Архитектура и поток данных

### Клиентский поток

1. Пользователь взаимодействует с Alpine-компонентом `app`.
2. Модули `auth.js`, `assets.js`, `risks.js`, `measures.js` и `ui.js` изменяют состояние и вызывают методы API-обёртки.
3. `src/database.js` сохраняет совместимый с прежним UI интерфейс `db.*`, но вместо SQL.js выполняет HTTP-запросы к Express.
4. JWT добавляется в `Authorization: Bearer <token>`.
5. Полученные данные записываются в реактивные массивы `assets`, `risks`, `measures` и объект `criteria`.
6. Alpine автоматически обновляет HTML.

### Серверный поток

1. Express принимает запрос и разбирает JSON-тело.
2. Для защищённых маршрутов middleware `authenticate` проверяет JWT.
3. Идентификатор пользователя из токена помещается в `req.user.userId`.
4. Route handler выполняет Prisma-запрос с фильтрацией по `userId`.
5. Сервер возвращает JSON-ответ или структурированную ошибку.

Все маршруты `/api/criteria`, `/api/assets`, `/api/risks` и `/api/measures` защищены JWT. Маршруты `/api/auth/*`, `/api`, `/api/health` доступны без авторизации.

## 6. Авторизация

### Регистрация

`POST /api/auth/register`

```json
{
  "login": "user",
  "password": "password123"
}
```

Пароль должен содержать минимум 6 символов. Сервер хеширует его через bcrypt и возвращает JWT вместе с публичными данными пользователя.

### Вход

`POST /api/auth/login`

Возвращает:

```json
{
  "token": "jwt-token",
  "user": {
    "id": "user-id",
    "login": "user",
    "createdAt": "..."
  }
}
```

### Выход

`POST /api/auth/logout`

JWT stateless, поэтому сервер не ведёт список отозванных access-токенов. Выход выполняется удалением токена на клиенте; endpoint существует для единообразия API.

### Обновление токена

`POST /api/auth/refresh`

Принимает текущий токен в теле `{ "token": "..." }` или в заголовке `Authorization` и возвращает новый access-токен.

## 8. Модель данных

Prisma-схема находится в `prisma/schema.prisma`.

- **User** — логин, хеш пароля и дата регистрации;
- **Criteria** — уникальный набор критериев пользователя;
- **Asset** — актив пользователя, его стоимость и приоритет;
- **Risk** — угроза, уязвимость, исходные параметры риска и остаточный риск;
- **Measure** — защитная мера, стоимость и проценты снижения.

Связи:

- один пользователь имеет много активов, рисков и мер;
- один пользователь имеет один набор критериев;
- актив имеет много рисков;
- риск принадлежит активу;
- риск может быть связан с одной мерой;
- при удалении актива связанные риски удаляются каскадно;
- при удалении меры связи с рисками снимаются.

Все операции с бизнес-данными ограничиваются текущим `userId`, поэтому пользователь не должен получать данные другого пользователя даже при наличии чужого идентификатора записи.

## 9. Формулы и бизнес-логика

Расчёты находятся в `src/calculations.js` и `src/dashboard.js`, а не на сервере.

### Исходный риск

```text
Риск = Ущерб × Вероятность × Приоритет актива
```

### Остаточный риск

```text
Остаточный риск =
  (Ущерб × (1 − Снижение ущерба / 100)) ×
  (Вероятность × (1 − Снижение вероятности / 100)) ×
  Приоритет
```

### Ожидаемый ущерб

```text
Ожидаемый ущерб = Баллы риска × Стоимость 1 балла риска
```

### ROSI

```text
ROSI = (Снижение потерь / Стоимость меры) × 100%
```

### Net ROSI

```text
Net ROSI = ((Снижение потерь − Стоимость меры) / Стоимость меры) × 100%
```

Клиент сохраняет вычисленные значения `score` и `residualScore` на сервере вместе с исходными параметрами, чтобы после повторной загрузки интерфейс отображал тот же результат.

## 10. Миграция с локальной базы

Ранее приложение использовало SQL.js и сохраняло SQLite-файл в `localStorage`. Эта схема удалена из рабочего потока:

- SQL.js больше не подключается в `index.html`;
- PostgreSQL является источником данных;
- `localStorage` используется только для JWT и краткой сессии;
- старые данные из `securityAppDb` автоматически не переносятся;
- после миграции пользователь должен зарегистрироваться заново.

## 12. Известные ограничения и дальнейшее развитие

- текущая Prisma-команда использует `db:push`; для production следует добавить версионируемые Prisma migrations;
- access-токен хранится в `localStorage`, что удобно для текущего SPA, но при повышенных требованиях безопасности стоит перейти на secure, httpOnly cookie-сессию;
- logout не отзывает уже выданный stateless JWT;
- сервер принимает часть числовых полей через `Number(...)`; для production рекомендуется вынести строгую валидацию DTO в отдельный слой;
- UI сохраняет legacy-совместимую обёртку `db.*`, чтобы не менять все Alpine-модули одновременно;
- расчёты намеренно остаются на клиенте, поэтому сервер не является источником математической валидации результата.
